# 轨道 1.9 — Network Scaling 网络扩展（`au4a-scale`）

`v1.9.1 → v1.9.9` ｜ 中版本标题：**Network Scaling 网络扩展** ｜ 负责：track-safety

把「网络结构的 Scaling Law」形式化：**节点数 / 交互复杂度 / 算力预算**如何决定**群体智能水平**，
并给出可复现的容量顶点裁决与论文稿。

## 0. 先说清楚边界（证据分级）

* 本轨道是**确定性聚合模型**（解析式实现）：10k 节点在**秒级**评估完，内存有界
  （O(1) 分配，不随 N 增长）。代码里**没有** 10k 线程、没有网络、没有真实压测。
* 因此「10k 节点」的证据等级是 **cpu-proto（模型推论）**，不是 `verified` 的实测吞吐；
  `verified` 只用于：本机跑出的数值、与解析式的逐点一致性、秒级/内存有界的实测约束。

## 1. 模型与单位（数学表达先于代码）

记节点数 `n`，参数 `(N0, α, p0, c)`：

| 量 | 表达式 | 单位 |
|---|---|---|
| 交互复杂度 | `E(n) = n·(n−1)/2` | 对（需要协调的连接） |
| 单节点有效吞吐 | `p(n) = p0·N0^α / (N0^α + n^α)` | milli/节点/epoch |
| 群体吞吐 | `T(n) = n·p(n)` | milli/epoch |
| 编排开销 | `O(n) = c·E(n)/1000` | milli/epoch |
| 净收益 | `G(n) = T(n) − O(n)` | milli/epoch |
| 完成率 | `C(n) = min(10000, 10000·T(n)/D)` | bp |
| 开销占比 | `R(n) = 10000·O(n)/T(n)` | bp |
| 边际收益 | `ΔT(n) = T(n+1) − T(n)` | milli/epoch |

**极值点（数学结论）**：`dT/dn = 0 ⟺ (α−1)·n^α = N0^α`，即
`n* = N0 / (α−1)^(1/α)`。α=1 时不存在内部极值（只饱和）；α=2 时 `n* = N0`；
α=3 时 `n* ≈ 0.794·N0`。**α > 1 才有容量顶点**——这是 v1.9.4 裁决规则的数学依据。

**单位约定**：`_milli` = 千分之一任务/epoch；`_bp` = 万分之一（10000 bp = 1.0）。
全部整数运算（基元层的规范 JSON 禁止浮点）。

**整数取整的实际影响（诚实说明）**：`p(n)` 向下取整，`p0` 很小时相邻 n 的 `T(n)`
可能在峰后短暂持平（每节点 1 milli 的截断 × n）。判断峰值时用 `p0 ≥ 10^6 milli`
或局部平均；度量误差上界 = 每节点 1 milli。

## v1.9.1 缩放定律度量

**目标**：把上表的度量落成整数实现，并证明「数学表达 = 代码 = 数值测试」。

**交付物**

* `src/metrics.rs`：`ScalingParams { n0, alpha, p0_milli, interaction_cost_milli }`（含 `validate`
  与 `has_interior_vertex`）、`interaction_complexity`、`coordination_base`、
  `effective_per_node_milli`、`aggregate_throughput_milli`、`orchestration_overhead_milli`、
  `net_throughput_milli`、`completion_bp`、`overhead_ratio_bp`、`marginal_gain_milli`、
  `analytic_vertex_floor`（整数二分求最大的 n 满足 `(α−1)·n^α ≤ N0^α`）。
* `src/lib.rs`：`self_check`（4 项真实断言）、`results_json`、`scenario`（4 个档位的度量表）。

**验收（8 个测试）**

* 手算一致：`p(N0) = p0/2`、`p(100)=500`、`T(100)=50000`、`p(10)=990`、`T(10)=9900`。
* **独立复算**：测试用 `u128` 直接按公式重算，与实现逐点相等（n=1,7,50,100,250,1000）。
* α=2 有峰值（`T(100) > T(1000)`）；α=1 严格单调（10→100→1k→10k）。
* 解析极值点与离散 argmax 相差 ≤ 1（α=2 → 1000；α=3 → 793）。
* 编排开销二次增长：`O(2000)/O(1000) ∈ [3.8, 4.2]`（bp 表达）；成本高时净收益为负。
* 完成率饱和在 10000 bp；`demand == 0` 被拒。
* 边际收益：顶点前为正、顶点后为负（用 `p0 = 10^6` 避免取整干扰）。
* 参数准入（n0=0 / α∉[1,3] / p0≤0 / c<0 全部拒绝）；参数 JSON 可规范化（无浮点）。

**证据**：`cargo test -p au4a-scale` → **8 passed / 0 failed / 0 warning**（本 crate；
2026-10-04 本机 Windows，log `_forangent\logs\1.9-v1.9.1.log`）。等级 `verified`（本机执行）。

**状态**：done（快照 `_forangent\snapshots\v1.9.1`）。

## v1.9.2 实验框架

**目标**：把「档位 × 参数」变成可复现、可**内容寻址**的实验报告。

**交付物**：`src/harness.rs`（`ExperimentConfig` / `Row` / `ExperimentReport` / `run`）；
`src/lib.rs` 的 `scenario` 改用框架产出报告。

**接口**

```rust
pub struct ExperimentConfig { pub nodes: Vec<u64>, pub params: ScalingParams, pub demand_milli: i64 }
pub struct Row { pub nodes, per_node_milli, aggregate_milli, overhead_milli, net_milli,
                 completion_bp, overhead_ratio_bp, marginal_gain_milli, step_gain_milli }
pub struct ExperimentReport { pub config, pub rows, pub digest }
pub fn run(config: &ExperimentConfig) -> CoreResult<ExperimentReport>;
```

* `digest = canonical_hash(rows)`：两个 Agent 交换 digest 即可确认「是不是同一份实验」。
* 框架**不引入第二套算法**：每一行的每个字段都直接调用 `metrics` 的函数。
* `step_gain_milli` 是**档位间**收益差（最后一档为 0）；`marginal_gain_milli` 是模型定义的
  `T(n+1) − T(n)`。两者在 v1.9.4 的裁决里分工不同：前者看档位尺度，后者看局部斜率。

**验收（新增 6 个测试，累计 14 个）**

* 每行 8 个字段与 `metrics` 逐字段相等（框架零算法漂移）。
* 两次 `run` 完全相同、digest 相同且等于 `canonical_hash(rows)`。
* α=3/N0=100 场景：相邻档位收益在顶点后转负（1k 档 `step_gain < 0`），末档为 0。
* `peak()` 取吞吐最大档位，并列取较小节点数。
* 空档位/重复档位/降序档位/0 档位/`demand=0`/非法参数全部被拒。
* 报告 JSON 可规范化（无浮点），配置可 JSON 往返。

**证据**：`cargo test -p au4a-scale` → **14 passed / 0 failed / 0 warning**（本 crate；
log `_forangent\logs\1.9-v1.9.2.log`）。等级 `verified`。**状态**：done（快照 `v1.9.2`）。
