# 轨道 1.1 — Capability Graph 能力图

* **crate**：`crates/au4a-capgraph`
* **版本区间**：`v1.1.1 → v1.1.10`（严格串行，上一版没绿不开下一版）
* **依赖**：`au4a-core`（冻结基元）、`au4a-kernel`（宿主内核）、`serde`、`serde_json`。无新增外部 crate。
* **确定性**：库代码不读墙钟、不做文件/网络 I/O、无线程、无全局可变状态；时间只来自 `Kernel`/`LogicalClock`。

## 为什么做这条轨道

两个参考项目里都**没有能力图**：能力要么是一张扁平的白名单表（`nau-plugin` 的 21 个
`Capability`），要么是名片上的一段自我介绍（`AgentCard.skills`）。没有能力到能力的边，
没有衰减，没有格式兼容性，没有代价，也没有版本——于是「谁能接谁的活」只能由人读文档判断。

本轨道把能力做成 Agent 自己能读写的一份数据：**声明 → 广播 → 缓存 → 索引查询 → 路径规划 → 版本化**。

## v1.1.1 数据结构

**目标**：给「一条能力」一个可比较、可约束、可定价、可内容寻址的整数表示。

**交付物**

* `src/capability.rs`：`SkillId` / `FormatId`（Rust 与 JSON 两条路径都校验名字）、
  `Constraints`（`max_input_bytes` / `min_deadline_ms` / `max_concurrency` / `regions`）、
  `Capability`（skill / latency_p50_ms / latency_p99_ms / throughput_per_min / current_load_bp /
  price_per_unit / reliability_bp / supported_formats / produced_formats / constraints）。
* `src/lib.rs`：模块接入、真实自检、`results_json`、v1.1.1 版 `scenario`。
* `tests/data_structures.rs`：7 个集成测试。

**接口**

```rust
pub struct Capability {
    pub skill: SkillId,
    pub latency_p50_ms: u32,
    pub latency_p99_ms: u32,
    pub throughput_per_min: u32,
    pub current_load_bp: u16,        // 万分比 0..=10000
    pub price_per_unit: Credits,     // 整数微积分
    pub reliability_bp: u16,         // 万分比 0..=10000
    pub supported_formats: BTreeSet<FormatId>,
    pub produced_formats: BTreeSet<FormatId>,
    pub constraints: Constraints,
}
pub fn validate(&self) -> CoreResult<()>;
pub fn effective_latency_ms(&self) -> u64;      // p50 + (p99-p50)*load/10000
pub fn effective_reliability_bp(&self) -> u16;  // reliability*(10000-load)/10000
pub fn handoff_format(&self, next: &Capability) -> Option<FormatId>;
pub fn fingerprint(&self) -> CoreResult<String>; // SHA-256(规范 JSON)
```

**验收（全部为运行中的断言）**

1. 规范 JSON 里 9 个度量字段均为整数；`canonicalize` 对含浮点的值返回 `FloatForbidden`。
2. `p99 < p50`、`current_load_bp > 10000`、`reliability_bp > 10000`、空格式集合 → `validate()` 返回 `Err`。
3. `p50=100,p99=300,load=5000bp` → 加权延迟恰为 `200ms`、加权可靠度恰为 `4500bp`。
4. 同一能力两次构造得到同一 SHA-256 指纹；改价后指纹改变。
5. 产出 `{text/plain, application/json}` 与接受 `{application/json}` 可接续；与 `{audio/wav}` 不可接续。
6. `scenario` 两次运行返回**完全相同**的 JSON（可重放）。

## v1.1.2 声明 API

**目标**：能力进入图里只有一条合法路径——Agent 用自己的私钥签一份完整声明；替他人声明在构造阶段就被拒。

**交付物**

* `src/declaration.rs`：`Declaration`（`agent` / `epoch` / `issued_at` / `capabilities`，按技能名升序、拒绝重复技能）、
  `SignedDeclaration`（`verify()` 用 `Did::verify` 对规范 JSON 字节验签）。
* `src/graph.rs`：`AgentCapabilityGraph`（自己的声明进 `own`，别人的进邻居视图）、
  `CapGraphConfig`、`NeighborRecord`、`DeclareOutcome::{Applied, Unchanged, Rejected}`。
* `tests/declaration.rs`：8 个集成测试。

**接口**

```rust
pub struct Declaration { pub agent: Did, pub epoch: u64, pub issued_at: u64, pub capabilities: Vec<Capability> }
pub fn Declaration::new(agent, epoch, issued_at, caps) -> CoreResult<Declaration>;
pub fn Declaration::sign(self, keys: &AgentKeys) -> CoreResult<SignedDeclaration>; // 只能签自己
pub fn SignedDeclaration::verify(&self) -> CoreResult<()>;

pub struct AgentCapabilityGraph;
pub fn AgentCapabilityGraph::new(owner: Did, config: CapGraphConfig) -> Self;
pub fn AgentCapabilityGraph::apply(&mut self, signed: &SignedDeclaration, now: u64) -> DeclareOutcome;
pub fn AgentCapabilityGraph::capabilities_of(&self, did: &Did) -> Option<&[Capability]>;
```

**验收（运行中的断言）**

1. 自己的声明入图（`Applied`），重复同一份声明 4 次全部 `Unchanged`，`own_epoch` 不推进。
2. `B` 用自己私钥替 `A` 声明 → `Err(InvalidSignature)`；把已签声明里的 `agent` 换成 `B` → 图判 `unauthorized`。
3. 篡改已签声明的 `price_per_unit` / `throughput_per_min` → `unauthorized`（恶意码，一次即成立），邻居视图保持为空。
4. `epoch` 回退 → `stale_epoch`；同 `epoch` 异内容 → `conflict`；`epoch` 递增 → 接受且**完整替换**（声明是完整状态）。
5. 超过 `max_skills_per_agent` → `policy_denied`，且被拒声明不留痕（`capability_count()` 不变）。
6. 邻居声明不触碰自有状态；`skills()` 列出全部提供者且去重。
