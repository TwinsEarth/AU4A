# 轨道 1.3 — Portable State 可移植状态（v1.3.1 → v1.3.10）

* crate：`crates/au4a-state`
* 依赖：`au4a-core`（冻结基元）、`au4a-kernel`（宿主内核）、`serde`、`serde_json`（无其它依赖）
* 一句话：Agent 从节点 A 迁到节点 B 时，**文件系统 / 内存 / 上下文**三区状态完整恢复；
  快照内容寻址 + Ed25519 签名；迁移走**两阶段提交**（prepare → commit → confirm，失败回滚，
  目标节点不留部分状态）；传输走**块级增量 diff**（三区 set/del，可续跑）。

## 0. 这一条轨道在证明什么

Agent 是主体，主体必须能**搬家而不丢自己**。所以本轨道的验收只有一句话：

> 迁移完成后，目标节点上的状态与源状态**逐字节一致**（规范 JSON 哈希相等），
> 且任何被替换、篡改、半途中断的状态都不能冒充「已迁移」。

三区缺一不可：只搬文件不搬上下文，回来的是一个失忆的进程，不是同一个 Agent。

### 两个哈希，别混用

| 哈希 | 覆盖 | 用途 |
|---|---|---|
| `StateSnapshot::root` | `(agent, blocks, node, epoch)` | 快照**文档**标识：内容寻址 + 篡改检测 |
| `StateSnapshot::content_root` | `(agent, blocks)` | 状态**内容**标识：迁移等价性验收 |

原因：迁移后「来源节点」「冻结时刻」这些**出处**必然变，但状态内容不能变。
把两者塞进同一个哈希，迁移就永远无法自证「我还是我」。

### 错误码映射（冻结的 `CoreError` 只有 16 个变体，不够用）

| 本轨道的语义 | `CoreError` | 内核 `RefusalCode` |
|---|---|---|
| 帧/快照/块结构不可解析 | `Encoding` | `Malformed` |
| 摘要、root、签名不符（篡改/替换） | `InvalidSignature` | `Unauthorized` |
| delta 的 base 不是预期起点（过期/竞争） | `InvalidSignature` | `StaleEpoch` |
| 2PC 目标节点已被占用 | `DuplicateAgent` | `Conflict` |
| 超出容量（块数/单块大小/帧大小） | `FrameTooLarge` | `ResourceExhausted` |
| 注入的故障（演练用） | `Overflow` | `Timeout` / `Degraded` |

内核的 `RefusalCode` 才承载完整语义；`CoreError` 是冻结的最小公共集，映射关系写在这里，
代码里也逐条注明了为什么。**只有 `malformed` / `unauthorized` 单次即恶意**，其余都是竞争语义。

  ```rust
  pub fn StateSnapshot::root(&self) -> &str            // 文档标识（含 node/epoch）
  ```

    （重复块幂等、缺块点名、断点续跑、拼装）、`send_delta` / `send_chunks` / `pull_into_session`。
  * `tests/v132_transfer.rs`：11 个集成测试。
* **接口**
  ```rust
  pub fn StateDelta::between(from: &StateSnapshot, to: &StateSnapshot) -> CoreResult<StateDelta>
  pub fn StateDelta::apply_to(&self, base: &StateSnapshot) -> CoreResult<StateSnapshot>
  pub fn StateDelta::apply_moved(&self, base, node, epoch) -> CoreResult<StateSnapshot>
  pub fn StateDelta::chunked(&self, max_ops: usize) -> CoreResult<Vec<DeltaChunk>>
  pub fn send_chunks(net, from, to, delta, max_ops, start, count) -> CoreResult<TransferReport>
  pub fn pull_into_session(net, node, session) -> CoreResult<(TransferSession, usize, usize)>

  pub fn TransferSession::resume_from(&self) -> usize
  ```
* **验收**
  1. diff 在 **fs / memory / context 三区**都产生 set 与 del；`per_zone()` 计数与断言一致。
  2. `apply_to` 后 `content_root` 与目标快照相等；逐块内容一致。
  3. **base 不对**（用目标当 base / 换过 root）→ `Err(InvalidSignature)`（语义：`StaleEpoch`）。
  4. 断线注入：第一段 2 块送达、第二段全丢 → `drop_pending` 计数正确、`missing()` 点数正确 →

  6. 跨传输会话的块 → `Err(InvalidVersion)`；不同 Agent 的 diff → `Err(InvalidDid)`。
  7. 帧前缀校验：截断 `FrameTruncated`、超 1 MiB `FrameTooLarge`（在分配前拒绝）。

    **没有真实网络**：没有真实丢包/TLS/对端作恶，只有本地双节点内存通道。

## v1.3.3 签名验证

* **目标**：内容寻址 + Ed25519 签名。**篡改或替换的快照必须被拒**，而且
  「签名有效」与「这是我要的那份」要分成两道闸门——只做前者，重放攻击就畅通无阻。
* **交付物**
  * `src/signed.rs`：`SignedSnapshot`（sign / verify / verify_policy / 线格式帧往返）、
    `SnapshotPolicy`（agent + content_root + min_epoch）、`VerifiedSnapshot`
    （**只有验过的快照才有这个类型**，且刻意不实现 `Deserialize`）。
  * `tests/v133_signature.rs`：16 个集成测试。
* **接口**
  ```rust
  pub fn SignedSnapshot::sign(snapshot: StateSnapshot, keys: &AgentKeys) -> CoreResult<SignedSnapshot>
  pub fn SignedSnapshot::verify(&self) -> CoreResult<()>                      // 结构与签名
  pub fn SignedSnapshot::verify_policy(&self, policy: &SnapshotPolicy) -> CoreResult<VerifiedSnapshot>
  pub fn SignedSnapshot::to_frame(&self) -> CoreResult<Vec<u8>>               // 4B 长度前缀 + 规范 JSON
  pub struct SnapshotPolicy { agent, content_root: Option<String>, min_epoch: Option<u64> }
  pub struct VerifiedSnapshot { /* 私有字段；唯一构造路径是 verify_policy */ }
  ```
* **验收**
  1. 自签快照 `verify()` 通过；JSON 与帧往返后签名不变；同种子同状态签名**逐字节相同**（可重放）。
  2. **篡改**：改块内容（保留旧签名）→ `from_value` 拒；改签名 hex → `InvalidSignature`；
     空签名 → `NotSealed`；载荷版本不符 → `InvalidVersion`；伪造 `signer` 字段 → 拒。
  3. **替换/重放**：另一份「自己签名有效」的快照 → `verify()` 通过、`verify_policy` 拒
     （`InvalidSignature`）；用冒名者的状态冒充主人 → `InvalidDid`。
  4. **过期**：合法但 epoch 低于策略下限 → `InvalidVersion`，且 `verify()` 仍通过——
     竞争与恶意必须分开（内核里分别记 `stale_epoch` / `unauthorized`）。
  5. **替签**：Bob 给 Alice 的状态签字 → `InvalidSignature`。
  6. `scenario()` 里签名握手成立：目标节点用策略验证源节点发来的签名快照，
     `verified.content_root == target.content_root`（重建的状态 == Agent 亲笔签下的状态）。
* **证据**
  * `test_command`：`cargo test -p au4a-state`
  * 结果：lib 44 + `v131` 13 + `v132` 11 + `v133_signature` 16 = **84 passed / 0 failed / 0 warning**
  * 日志：`E:\DS\_forangent\logs\1.3-v1.3.3.log`
  * `grade`：`verified`（真实 Ed25519 签名/验签，本机实跑；签名算法来自冻结基元层）
* **状态**：`done`

## v1.3.4 恢复协议（两阶段提交）

* **目标**：迁移**全有或全无**。prepare → commit → confirm；任意阶段失败回滚，
  **目标节点不得留下部分状态**。
* **为什么部分状态最危险**：它是「一半旧状态 + 一半新状态」的混合体，而两半各自都自洽，
  因此**没有内部矛盾可供自检发现**。所以协议不允许出现它，而不是事后去检测它。
* **设计：影子代 + 单点切换**
  ```text
  live 视图 = gen:<head>: 命名空间        （head 是唯一入口，一次 put 即切换）
  prepare : 把目标状态完整物化到 gen:<head+1>: 并读回校验   （live 不动）
  commit  : 把 head 从 n 改成 n+1                          （单次原子 put）
  confirm : 校验 live == 目标内容根，删旧代与意图记录
  rollback: 删影子代；若 head 已切换则拨回去（confirm 之前都合法）
  ```
  回滚是**状态驱动**的：只看 head 指向谁、影子代是哪一个，不相信内存里的阶段字段——
  因为真实崩溃恰好发生在「head 已切换、阶段字段还没推进」的那一瞬间。
* **交付物**
  * `src/recovery.rs`：`NodeStore`（代存储 + `flip_head` 唯一切换点 + 孤儿代检测）、
    `Migration`（prepare / commit / confirm / rollback + 阶段守卫）、`MigrationPlan`（tx 内容寻址）、
    `FaultInjector` / `FaultPoint`（5 个定点注入）、`migrate()`（失败自动回滚并返回证据）、
    `MigrationOutcome` / `MigrationReport`。
  * `tests/v134_two_phase.rs`：13 个集成测试。
* **接口**
  ```rust
  pub fn NodeStore::open(node, agent, store) -> CoreResult<NodeStore<S>>
  pub fn NodeStore::live_content_root(&self) -> CoreResult<String>
  pub fn NodeStore::write_generation(&mut self, gen, snapshot) -> CoreResult<usize>  // 拒绝写生效代
  pub fn Migration::prepare(&mut self, node, delta, signed, faults) -> CoreResult<PrepareReceipt>
  pub fn Migration::commit(&mut self, node, faults) -> CoreResult<CommitReceipt>
  pub fn Migration::confirm(&mut self, node, faults) -> CoreResult<ConfirmReceipt>
  pub fn Migration::rollback(&mut self, node) -> CoreResult<usize>                   // 幂等
  pub fn migrate(node, plan, delta, signed, faults) -> CoreResult<MigrationOutcome>
  pub enum FaultPoint { BeforeStaging, AfterStaging, BeforeFlip, AfterFlip, BeforeCleanup }
  ```
* **验收**
  1. 顺序正确时三个阶段依次推进；**prepare 之后 live 仍是 base**（这是 2PC 的关键断言）。
  2. 5 个注入点逐个注入故障 → 全部 `RolledBack`：`state_restored = true`、`orphans = 0`、
     意图记录已清、live 的**块集合整体等于 base**（逐块比对，不是只看哈希）。
  3. 任意注入后 live 的 `content_root ∈ {base, target}`，**不存在第三种可能**。
  4. 阶段守卫：commit 在 prepare 前、prepare 两次、confirm 在 commit 前、confirm 两次 → 全部 `Err`。
  5. rollback 幂等；已 confirm 的迁移拒绝回滚（否则两个节点会对「谁是权威」产生分歧）。
  6. 写生效代（`write_generation(head)`）被拒；被拒的迁移**不动 head、不留孤儿代**。
  7. rollback 在 `head` 已切换（AfterFlip）时能把 head 拨回去并恢复 base。
  8. 迁移可重放：同样输入 → 同样的 outcome JSON 与同样的 live 内容根。
* **证据**
  * `test_command`：`cargo test -p au4a-state`
  * 结果：lib 53 + `v131` 13 + `v132` 11 + `v133` 16 + `v134_two_phase` 13 = **106 passed / 0 failed / 0 warning**
  * 日志：`E:\DS\_forangent\logs\1.3-v1.3.4.log`
  * `grade`：`verified`（协议与故障注入全部本机实跑；存储是本地内存实现，
    但 2PC 的语义不依赖存储介质——换真实存储只需换 `StateStore` 实现）
* **状态**：`done`

## v1.3.5 一致性检查

* **目标**：让「恢复成功」成为一个**可以被检查**的结论：三区摘要 + 块级差异，
  把损坏定位到「区 + 键 + 类型（missing / extra / modified）」。
* **三种检查各管一段**
  * `compare(源, 恢复后)`：两份快照之间逐区逐块比对。
  * `compare_store(store, prefix, 期望)`：直接读**存储原始字节**，
    刻意不走 `read_snapshot`——因为「读不出来」本身就是要报告的一种损坏。
  * `audit_node(node)`：2PC 卫生（孤儿代、未完成迁移的意图、意图与 live 是否一致）。
* **交付物**
  * `src/integrity.rs`：`Finding` / `FindingCode`（8 类）、`ZoneReport`、`ConsistencyReport`、
    `StoreReport`、`NodeAudit`、`compare` / `compare_store` / `audit_node` / `summarize`。
  * `tests/v135_consistency.rs`：12 个集成测试。
* **接口**
  ```rust
  pub fn compare(left: &StateSnapshot, right: &StateSnapshot) -> CoreResult<ConsistencyReport>
  pub fn compare_store(store: &S, prefix: &str, expected: &StateSnapshot) -> CoreResult<StoreReport>
  pub fn audit_node(node: &NodeStore<S>) -> CoreResult<NodeAudit>
  pub enum FindingCode { Missing, Extra, Modified, BadKey, Unreadable, OrphanGeneration, UnfinishedMigration, IntentMismatch }
  pub struct ZoneReport { zone, left_root, right_root, equal, missing, extra, modified }
  ```
* **验收**
  1. 内容一致（出处不同）→ 报告干净：`identical = true`、0 处差异、三区 `zone_root` 两两相等。
  2. 三区各自损坏（改一块 / 删一块 / 加一块 / 塞一个坏键）→ 报告分别给出 1 条
     `modified` / `missing` / `extra` / `bad_key`，并且 `zone` 与 `key` 可读。
  3. `compare_store` 能发现「存储字节被改」，并给出观测到的内容根（与期望不同）。
  4. 只改 memory 一块时，fs 与 context 两区摘要**保持不变**——诊断粒度是区。
  5. 2PC 提交后 `compare(源, live)` 干净且逐块相等；回滚后 `compare(base, live)` 干净而
     `compare(target, live)` 不干净（回滚是真的）。
  6. 未完成的迁移在节点审计里可见（`unfinished_migration` + `intent_mismatch`）。
* **证据**
  * `test_command`：`cargo test -p au4a-state`
  * 结果：lib 59 + `v131` 13 + `v132` 11 + `v133` 16 + `v134` 13 + `v135_consistency` 11 = **123 passed / 0 failed / 0 warning**
  * 日志：`E:\DS\_forangent\logs\1.3-v1.3.5.log`
  * `grade`：`verified`
* **状态**：`done`

## v1.3.6 UDOS 集成（数据契约）

* **目标**：与 `E:\DS\UDOS` 建立**数据契约**——分布式存储语义对齐，**不引入依赖、不联网、
  不调用 Python**。
* **为什么是数据契约而不是依赖**：UDOS 是 Python 的世界模型/具身智能工程，AU4A 是 Rust 的
  Agent 宇宙。两者能共享的不是代码，而是**对象语义**：一个状态对象长什么样、怎么被寻址、
  怎么声明证据等级、怎么被另一个系统独立验证。
* **对齐点（逐条对 UDOS 现有实现）**

  | 本模块 | UDOS 对应物 | 对齐的证据 |
  |---|---|---|
  | `object_id = "sha256:<hex>"` | `udos.evidence.file_digest()` → `"{algo}:{hex}"` | 算法前缀格式一致 |
  | `grade` ∈ verified / cpu-proto / unverified | `udos.contracts.EvidenceGrade` | 三个等级、同一组字符串（测试断言） |
  | context 区 ↔ `TransferBundle` | `udos.topology.transfer.TransferBundle` | goal / todo / context / done / owner / trace 六字段同名 |
  | `bundle_fingerprint` | `udos.topology.transfer.state_fingerprint` | 规范 JSON 哈希、对键序不敏感 |
  | `claim()` | `udos.evidence.Claim` | key / statement / grade / method / artifact_digest |

* **交付物**
  * `src/udos.rs`：`UdosObject`（schema/kind/object_id/collection/grade/provenance/payload）、
    `snapshot_to_object` / `object_to_snapshot`、`delta_to_object` / `object_to_delta`、
    `context_to_transfer_bundle` / `transfer_bundle_to_blocks`、`bundle_fingerprint`、
    `claim`、`contract_descriptor`、`contract_check`、`collection_manifest`、`delta_shape`。
  * `tests/v136_udos.rs`：14 个集成测试。
* **接口**
  ```rust
  pub const SCHEMA: &str = "udos.object/1";
  pub fn digest_of(value: &Value) -> CoreResult<String>            // "sha256:<hex>"
  ```

## v1.3.7 性能优化

* **目标**：在不读墙钟的前提下证明「更省」。本轨道禁止计时，所以「更快」改成
  **可复算的工作量**：哈希次数、物化块数、续跑省下的操作数——同样输入给同样数字。
* **三处真实的省力**
  1. **块摘要复用**（`DigestCache`）：摘要只取决于 `(zone, key, 规范 JSON 字节)`，
     缓存键就是这三者。命中即输入逐字节相同 ⇒ SHA-256 确定 ⇒ 摘要必然相同。
     所以复用不是「赌一把」，而是同一条数学事实的复用（错配需要哈希碰撞）。
  2. **只物化变动的块**（`perf::plan` + `perf::materialize`）：先按摘要算出变更清单，
     再只对变动块搬运 value；未变块连一次 `value.clone()` 都不发生。
  3. **只补缺失的块**（续跑）：断线重连只传缺口，`ops_skipped` 记录省下的操作数。
* **交付物**
  * `src/perf.rs`：`WorkCounter`（8 个确定性计数器，**无时间字段**）、`DigestCache`、
    `DeltaPlan` / `plan` / `materialize`、`resume_savings`、`measure_transfer` /
    `measure_receive`、`generation_write_estimate`、`summary`。
  * `src/snapshot.rs`：新增 `StateBlock::new_cached`（只允许由 `DigestCache` 驱动的复用路径调用，
    crate 内可见；不变式由缓存正确性保证）。
  * `tests/v137_perf.rs`：10 个集成测试。
* **接口**
  ```rust

                           blocks_materialized, store_writes, ops_transferred, ops_skipped }

  pub fn DigestCache::capture_raw(agent, node, epoch, blocks, counter) -> CoreResult<StateSnapshot>
  pub fn plan(from, to) -> CoreResult<DeltaPlan>            // 只比摘要，不搬 value
  pub fn materialize(from, to, plan, counter) -> CoreResult<StateDelta>
  ```
