# 轨道 1.4 — Economic Autonomy 经济自主

* **crate**：`crates/au4a-economy`
* **版本区间**：v1.4.1 → v1.4.10（10 个小版本，严格串行）
* **负责人**：track-economy
* **依赖**：`au4a-core`（冻结基元）、`au4a-kernel`（宿主内核）、`serde`、`serde_json`
* **人类的位置**：人类只能看三个只读投影（进度 / 结果 / 收益），**不能**发起、批准、定价、裁决。
  本轨道不提供任何写路径给人类。

## 贯穿全轨道的三条不变式

1. **账本守恒**：一切账务走 `au4a_core::Ledger`，每个写路径末尾调用
   `check_conservation()`：`Σ可用 + Σ锁定 + 罚没 == 已发行`。
2. **整数经济**：金额只用 `Credits`（微积分），比率只用基点（1 bp = 0.01%）。
   库代码不含浮点，规范 JSON 直接拒绝浮点，所以同输入必然同输出、可重放。
3. **证据闸门**：`EvidenceGrade::Unverified` 永远不可结算（由 `Kernel::settle` 强制）；
   `CpuProto` 只能结算不超过 `KernelConfig::cpu_proto_settle_cap` 的金额。
   真实链上执行属于 **v1.8**，本轨道只做**兑换路由决策与账务**，绝不伪造链上成功。

## v1.4.1 余额管理

**目标**：让每个 Agent 自己申报并执行余额策略（运营底线 / 目标质押比例 / 单笔支出上限），
拒绝路径与执行路径分离，任何拒绝都不改动账本一个字节。

**交付物**

* `src/balance.rs`：`BalancePolicy`、`SpendVerdict`、`check_spend`、`spend`、`autostake`、
  `spendable`、`stake_target`、`stake_deficit`、`delta`、`BalanceReport`、`BalanceManager`。
* `src/lib.rs`：`self_check()` 真实跑两条余额自检；`scenario()` 在共享内核上跑通
  「注册 → 自主申报策略 → 支付 → 被拒绝 → 自主质押 → 守恒断言」。

**接口（本版新增 public 项）**

```rust
pub struct BalancePolicy { pub reserve_floor: Credits, pub stake_target_bp: i64, pub max_spend_bp: i64 }
pub enum SpendVerdict { Allow, ZeroAmount, BelowReserve, OverSingleCap }
pub fn check_spend(ledger: &Ledger, who: &Did, amount: Credits, policy: &BalancePolicy) -> CoreResult<SpendVerdict>
pub fn spend(ledger: &mut Ledger, from: &Did, to: &Did, amount: Credits, policy: &BalancePolicy) -> CoreResult<Credits>
pub fn autostake(ledger: &mut Ledger, who: &Did, policy: &BalancePolicy, budget: Credits) -> CoreResult<Credits>
pub fn spendable(ledger: &Ledger, who: &Did, policy: &BalancePolicy) -> CoreResult<Credits>
pub fn stake_target / stake_deficit(ledger: &Ledger, who: &Did, policy: &BalancePolicy) -> CoreResult<Credits>
pub fn delta(before: &Account, after: &Account) -> AccountDelta
pub fn assert_conserved(ledger: &Ledger) -> CoreResult<()>
pub struct BalanceManager { /* 每个 Agent 只申报自己的策略；无「替别人设定」的方法 */ }
```

**判定表（纯函数 `check_spend`，顺序即优先级）**

| 条件 | 判定 | 写路径动作 |
|---|---|---|
| `amount == 0` | `zero_amount` | 返回 `CoreError::ZeroAmount`，账本不变 |
| `available < reserve_floor + amount` | `below_reserve` | 返回 `CoreError::InsufficientFunds`，账本不变 |
| `amount > available × max_spend_bp / 10000` | `over_single_cap` | 返回 `CoreError::InsufficientFunds`，账本不变 |
| 其余 | `allow` | `transfer` → `check_conservation()` |

越界参数（基点 < 0 或 > 10000）在申报策略时即被拒绝：负数 → `NegativeAmount`，
越界 → `InvalidKind`（`CoreError` 是冻结枚举，没有 `OutOfRange`，映射固定且已写入文档）。

**验收**

* `an_allowed_spend_moves_exactly_the_amount`：断言支付 300 后 a 可用 700、b 可用 300、守恒成立。
* `a_spend_that_would_break_the_reserve_floor_is_refused_and_changes_nothing`：
  可用 400 / 底线 100 时支出 301 被拒，拒绝后双方余额与拒绝前逐字节相同。
* `the_single_transaction_cap_is_enforced`：可用 10 000、`max_spend_bp=1000` 时
  1 001 被拒、1 000 通过。
* `autostake_locks_up_to_the_target_and_never_crosses_the_floor`：目标 = 总资产 × 20%，
  达标后再次补足返回 `ZeroAmount`（不静默成功）。
* `conservation_holds_across_a_scripted_sequence`：支付 / 质押 / 转移 / 罚没 6 步，
  每步后 `check_conservation()` 成立，最后罚没精确等于锁定余额。

## v1.4.2 定价策略

**目标**：Agent 用**自己**的信誉分 / 能力稀缺度 / 当前负载算出报价并广播，买方在共享内核里
「发现彼此」并按整数单价挑选供给方。全程整数基点运算，无浮点，同输入必然同输出。

**定价公式（[`pricing::quote`]，纯函数）**

```text
信誉折扣   = reputation_bp × reputation_discount_max_bp / 10000      （向下取整）
稀缺溢价   = scarcity_bp   × scarcity_premium_max_bp   / 10000
负载溢价   = load_bp       × load_premium_max_bp       / 10000
multiplier = clamp(10000 + 负载溢价 + 稀缺溢价 − 信誉折扣, min_bp, max_bp)
unit_price = max(base_price × multiplier / 10000, 1)
```

默认系数：信誉最多降 20%、稀缺最多加 30%、负载最多加 50%，总乘数夹在 `[5000, 20000]` bp。
价格下限为 1 微积分，报价绝不会塌缩成 0（0 额结算在账本层是非法调用）。

**交付物**

* `src/pricing.rs`：`PriceInputs`、`PriceKnobs`、`PriceComponents`、`PriceQuote`
  （`total_for` / `fingerprint`）、`quote`、`unit_price`。
* `src/lib.rs`：`PRICE_KIND = "economy.price"` 公告类型；场景新增「两个供给方各自定价 →
  签名广播 → 买方 `drain` 验签 → 按 `(unit_price, provider)` 升序取最便宜者」。
* `self_check()` 新增 `pricing.reproducible`（两次报价与内容哈希一致 + 钉住具体数值）
  与 `pricing.monotonicity`（0→10000 扫描负载与信誉）。

**接口（本版新增 public 项）**

```rust
pub struct PriceInputs { pub base_price: Credits, pub reputation_bp: i64, pub scarcity_bp: i64, pub load_bp: i64 }
pub struct PriceKnobs { /* 5 个基点系数，DEFAULT 常量 */ }
pub struct PriceComponents { pub reputation_discount_bp: i64, pub scarcity_premium_bp: i64, pub load_premium_bp: i64 }
pub struct PriceQuote { pub inputs, pub components, pub multiplier_bp: i64, pub unit_price: Credits }
pub fn quote(inputs: &PriceInputs, knobs: &PriceKnobs) -> CoreResult<PriceQuote>
pub fn unit_price(inputs: &PriceInputs, knobs: &PriceKnobs) -> CoreResult<Credits>
pub const PRICE_KIND: &str = "economy.price";
```

**验收**

* `concrete_numbers_are_pinned`：base 1 000 000、信誉 8000、稀缺 2000、负载 4000 →
  折扣 1600 / 稀缺 600 / 负载 2000 / 乘数 11000 / 单价 **1 100 000**（逐项断言）。
* `the_same_input_always_gives_the_same_quote` + `the_quote_is_integer_only_and_canonicalizable`：
  两次报价相等、内容哈希相等，且报价能通过「拒绝浮点」的规范 JSON 编码。
* `load_up_price_up_never_down`：`load_bp` 从 0 扫到 10000 逐点断言价格不降；
  500bp 网格上断言**严格**递增。
* `reputation_up_price_down_never_up`：信誉 0→10000 逐点断言价格不升；500bp 网格严格递减。
* `scarcity_up_price_up`：稀缺度每 +500bp 价格严格上升。
* `clamps_bound_the_multiplier_on_both_ends`：`[9500, 12000]` 夹取在两端都生效。
* `a_price_never_collapses_to_zero`：base 1、满信誉 → 乘数 8000、单价仍为 1。
* `degenerate_inputs_are_refused`：base 0 → `ZeroAmount`；信誉 10001 → `InvalidKind`；
  负数 → `NegativeAmount`；`min > max` → `InvalidKind`。

## v1.4.3 自动兑换（路由决策）

**目标**：给出「系统积分 ↔ BTC/ETH」的兑换**路由决策表**与账务边界。本版只做决策 + 账务预留，
**绝不伪造链上成功**——真实链上执行属 v1.8。

**决策表（[`fx::route`]，纯函数，顺序即优先级）**

| # | 条件 | 动作 | 理由码 | 账务 |
|---|---|---|---|---|
| 0 | `amount == 0` | 拒绝 `ZeroAmount` | — | 不动 |
| 1 | Agent 显式偏好内部结算 | `keep_internal` | `preferred_venue` | 内部转账 |
| 2 | `amount < onchain_min_amount` | `keep_internal` | `below_onchain_minimum` | 内部转账 |
| 3 | `slack_ticks < urgency 所需时间片` | `defer` | `deadline_too_tight` | **不动** |
| 4 | `venue_fee_bp > max_fee_bp` | `defer` | `fee_above_threshold` | **不动** |
| 5 | 其余 | `route_onchain`（v1.8 执行） | `cheapest_venue` / `preferred_venue` | 预留（可用→锁定） |

默认表：BTC 120bp / ETH 80bp（费率相同按场所名升序，确定性）、200 微积分以下不上链、
费率上限 150bp、普通时效需 ≥20 时间片、加急需 ≥60。

**「不伪造链上成功」是类型性质，不是文档承诺**

* `ChainExecution` 只有 `PendingV18` / `NotApplicable` / `NotRequested` 三个变体，**没有** `Executed`；
* `ChainExecution::executed()` 是 `const fn`，恒返回 `false`；
* `IntentStatus` 只有 `AwaitingChainExecution` 一个变体；
* `ExchangeIntent::on_chain_success()` 恒返回 `false`；
* 只有 `route_onchain` 的计划能被 `escrow_for_route` 预留，其余动作返回 `InvalidKind`。

**交付物**

* `src/fx.rs`：`Venue`、`Urgency`、`RouteAction`、`DecisionReason`、`ChainExecution`、
  `IntentStatus`、`RouteTable`、`ExchangeRequest`、`RoutePlan`、`ExchangeIntent`、`Release`、
  `ExchangeBook`、`route`、`fee_for`、`escrow_for_route`、`cancel_intent`、`apply_internal`。
* `src/lib.rs`：场景新增「150 内部 / 400+剩余12 缓办 / 400+剩余30 走 ETH（费用 3、到账 397）」，
  预留前先过 Agent 自己的余额策略；`self_check()` 新增 `fx.decision_table`、`fx.no_fake_chain`。

**验收**

* `small_amounts_stay_off_chain`：199 → `keep_internal` / `below_onchain_minimum`，费用 0、到账 199。
* `the_cheapest_venue_wins_with_integer_fee_math`：1000 → ETH，费用 `1000×80/10000 = 8`，到账 992。

## v1.4.4 质押管理

**目标**：Agent 自主质押 / 解质押 / 冷静期解锁，罚没与质押簿同步；准入线与份额上限由网络条款
固定，**不需要任何人批准**。冷静期用逻辑时钟，不读墙钟。

**账务语义**

| 动作 | 账本 | 质押簿 |
|---|---|---|
| `stake` 质押 | 可用 → 锁定 | `locked += amount`（校验准入线与份额上限） |
| `request_unstake` 解质押 | **不动**（仍然锁定，仍受罚没约束） | `locked -= amount`，加入 `unbonding`（`release_at = now + cooldown`） |
| `release_matured` 冷静期到点 | 锁定 → 可用（只解锁已到点的量） | 移除已到点的解绑记录 |
| `absorb_slash` 罚没同步 | 由调用方配对 `Ledger::slash` | `locked` 削减（不超过质押中余额） |
| `adopt` 认领既有质押 | **不动**（镜像账本上已有的锁定） | 登记头寸，不重复锁定 |

**不变式（被测试钉住）**：质押簿声称的承诺量 **永远不超过**账本实际锁定量。
之所以不是「等于」——链上兑换的在途预留也住在 `locked` 里（v1.4.3）；簿记可以少记，绝不能多记。

**交付物**

* `src/stake.rs`：`StakeTerms`（下限 / 冷静期 / 份额上限）、`Unbonding`、`StakePosition`
  （`unbonding_total` / `committed`）、`StakeBook`（`adopt` / `stake` / `request_unstake` /
  `release_matured` / `absorb_slash` / `position` / `total_locked` / `total_unbonding` /
  `assert_consistent` / `to_json`）。
* `src/lib.rs`：场景新增「认领注册质押 100 → 自主解质押 40 → 无头寸者被拒 → 冷静期 3 个逻辑
  时间片 → 释放 40」；`self_check()` 新增 `stake.self_custody`。

**验收**

* `staking_locks_funds_and_records_a_position`：质押 200 → 可用 800 / 锁定 200，簿账一致。
* `below_the_admission_line_is_refused` / `above_the_share_cap_is_refused`：
  99 < 下限 100 → `InsufficientStake`；501 > 上限（1000×50%）→ `InsufficientStake`。
* `unstaking_moves_lock_to_unbonding_without_moving_the_ledger`：解质押 150 后账本锁定仍为 400，
  头寸 `locked=250`、`unbonding=150`、`committed=400`。
* `unstaking_below_the_line_or_without_a_position_is_refused`：跌破准入线 → `InsufficientStake`；
  超过质押中量 → `InsufficientFunds`；无头寸 → `UnknownAgent`。
* `the_cooldown_is_exact_at_the_boundary`：`release_at = 25` 时 t=24 释放 0、t=25 精确释放 100。
* `slashing_is_bounded_and_the_book_follows`：罚没 10 000 被锁定余额约束为 300，簿记同步归零。
* `the_book_may_never_claim_more_than_the_ledger_holds`：账本被外部解锁后 `assert_consistent` 报错。
* `adopting_existing_stake_does_not_double_lock`：认领 150 不重复锁定；认领 151 → 拒绝。
* `totals_and_json_projection_are_integer_only`：聚合值与 JSON 投影无浮点。
* `degenerate_terms_are_refused`：份额上限 10001 → `InvalidKind`；负数 → `NegativeAmount`。

## v1.4.5 争议仲裁

**目标**：Agent 自主立案、自主投票、自主申诉；罚没**上限 = 锁定余额**，且申诉入口始终存在。
没有任何人类裁决路径（参考项目的 `Authority::Operator` 在这里被反向掉）。

**规则**

| 环节 | 规则 | 拒绝路径（冻结错误映射） |
|---|---|---|
| 立案 `open` | 证据不可为 `Unverified`；索赔额 > 0；不得自己告自己 | 证据不合法/自诉 → `InvalidKind`；零额 → `ZeroAmount` |
| 投票 `vote` | 仅 `Open`/`Voting`/`Appealed` 可投票；票权 0..=10000bp；一案一票 | 利益相关者 → `UnknownAgent`；重复投票/状态不符 → `InvalidKind` |
| 裁决 `rule` | 票数 ≥ 法定人数且支持票权 ≥ 阈值才罚没 | 票数不足/越序 → `InvalidKind` |
| 罚没额 | `min(索赔额, cpu-proto 上限, 锁定余额)`，`cap` 记录被谁截断 | 罚没永不越过锁定余额 |
| 申诉 `appeal` | 仅当事人、窗口内（`ruled_at + window`）、次数 ≤ `max_appeals`；重开投票（原票作废） | 非当事人 → `UnknownAgent`；其余 → `InvalidKind` |
| 结案 `close` | 仅 `Ruled` 可结案 | 越序 → `InvalidKind` |

**销毁不可逆**：申诉重裁**不会**退回已销毁的罚没；第二次裁决只会「确认或加重」
（`slashed` 与 `slashed_total` 分开记账，测试断言第二次驳回时本次罚没为 0、累计仍为 100）。

**错误码映射说明**：`CoreError` 是冻结枚举（16 个变体，没有 `Conflict`/`Unauthorized`），
因此模块内用两个具名辅助函数把语义固定下来——`state_conflict()` → `InvalidKind`、
`not_a_party()` → `UnknownAgent`——并写进本文档，不新增错误类型。

**交付物**

* `src/arbitration.rs`：`DisputeState`、`Vote`、`Appeal`、`PenaltyCap`、`Dispute`（`uphold_bp`）、
  `ArbitrationTerms`、`Ruling`、`is_admissible`、`Court`（`open` / `vote` / `rule` / `appeal` /
  `close` / `case` / `case_json` / `open_cases` / `total_slashed` / `to_json`）。
* `src/lib.rs`：场景新增「Unverified 立案被拒 → 立案 → 两票通过 → 罚没被锁定余额截断为 100 →

## v1.4.6 结算路由与收益归属

**目标**：把「钱怎么走」定成决策表；分成用整数最大余数法严格分完；人类操作者**只收收益**。

**结算路由决策表（[`settlement::route`]，纯函数）**

| # | 条件 | 路由 | 理由码 | 账务 |
|---|---|---|---|---|
| 0 | `total == 0` | 拒绝 `ZeroAmount` | — | 不动 |
| 1 | 证据 `Unverified` | `withheld` | `evidence_unverified` | **不动**（并留类型化拒绝） |
| 2 | `cpu-proto` 且超上限 | `withheld` | `cpu_proto_cap` | **不动** |
| 3 | 收款方有未结争议且策略要求托管 | `escrowed` | `payee_under_dispute` | 先锁定，裁决后放款/退回 |
| 4 | 其余 | `direct` | `evidence_ok` | 走 `Kernel::settle`（证据闸门 + 守恒） |

**分成（[`settlement::split_weights`]）**：最大余数法，权重之和必须恰好 10 000bp；
先向下取整，再把剩余逐个分给余数最大者（余数相同按下标升序，确定性）。
断言：`Σ分账 == 总额`（对 1..500 的全部总额都验证过），0 权重不产生凭证也不做零额转账。

**收益归属**：`Beneficiary::human_operator(did)` 的 `decision_rights()` 恒为 `IncomeOnly`、
`may_decide()` 恒为 `false`——人类操作者能收到 `Receipt`，但结构上没有提案 / 定价 / 投票 / 仲裁入口。
场景里的「人类操作者的数据资源」没有注册为 Agent，只通过分成收到 60 微积分。

**交付物**

* `src/settlement.rs`：`ProviderRole`、`BeneficiaryKind`、`DecisionRights`、`Beneficiary`、
  `RevenueShare`、`Receipt`、`SettlementRoute`、`SettlementPolicy`、`SettlementRequest`、
