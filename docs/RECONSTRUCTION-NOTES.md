# 历史版本树的重建与验证纪律（v2.4.0 补记）

> 这份笔记记录两件事：**7 个早期 tag 的历史树是怎么被重建的**，以及重建过程中用血换来的两条纪律。
> 它不是生成文件（不由 `tools/*.mjs` 产出），因此不会被重新生成覆盖。

## 一、问题：已发布的早期 tag 混入了"当时不存在"的内容

`crates/au4a-node`（平台层）只在 **v1.9.9** 打过逐版本快照。物化器（`tools/materialize.mjs`）的规则是
「按**文件**取 `seq <= 目标版本` 的最新快照」，未命中则回落到**当前工作树**。于是
`v1.0.10 … v1.6.10` 这 7 个 tag 的树里混进了最终版平台层与后期文档，`cargo test --workspace` 在这些 tag 上失败。

更隐蔽的一层：**第 11 轮里 10 条轨道同时发布 `.10` 收尾版本**，于是
`au4a-council`(1.7) 的同轮快照叫 `v1.7.10`、`au4a-chain`(1.8) 叫 `v1.8.10`、`au4a-scale`(1.9) 叫 `v1.9.9`——
**它们的 seq 都大于 `v1.6.10`**，被旧的"按 seq 重放"规则整体排除，导致这三个 crate 回落到工作树，
同一 crate 的 `src/` 与 `tests/` 来自不同轮次，编译直接失败（`unresolved import au4a_council::audit`）。

## 二、纪律 1：同源单元 = **crate 目录 + 该轨道的元数据**

"按 crate 取单一来源"**不够**。`crates/au4a-council/tests/claims.rs` 会校验
`docs/tracks/1.7.md` / `1.7.json` 是否覆盖该轨道**恰好 10 个小版本**。
只替换 crate 目录、不替换轨道元数据，测试会报
`轨道 1.7 必须恰好覆盖 10 个小版本（left: 9, right: 10）`。

**因此同源单元必须是：`crates/<crate>/**` + `docs/tracks/<track>.{md,json}`（按需含 `docs/DESIGN.md`/`DEV.md` 的对应小节）**，
一起取自同一个版本快照。物化器的"规则 0"已按此实现（按 crate 取单一来源 + 按**轮次**而非版本号筛选）。

## 三、纪律 2：本地闸门必须用**唯一** `CARGO_TARGET_DIR`

连续四轮修复都失败，最后定位到真正的凶手是**我自己的闸门脚本**：它复用了同一个
`CARGO_TARGET_DIR`，于是 `cargo` **重放了修复前的编译指纹**——内容已经改对，报错却一模一样地"重现"，
把我引向"快照语料不自洽"的错误结论，白追了四轮。

**闸门规则（`_forangent/gate-tag.mjs`）**：
1. 候选树 = **已发布 tag 树** + 只替换"内容上不是单一来源"的 crate（比对**逐文件 sha256**，不是文件名集合——只看文件名会漏判）；
2. 平台层 `au4a-node` 在早期 tag 保持骨架，不注入最终实现；
3. `CARGO_TARGET_DIR` 带时间戳**每次全新**；
4. **`cargo build --workspace --locked` 与 `cargo test --workspace --locked` 双绿，才允许 `force-move` tag**；
5. 最后交 **CI** 判定（CI 是裁判，不是我的自述）。

## 四、结果（CI 判定，非自述）

7 个 tag 全部重建并固化：`v1.0.10` `v1.1.10` `v1.2.10` `v1.3.10` `v1.4.10` `v1.5.10` `v1.6.10`。

```
CI: version line 10/10 green
  ok v1.0.10  ok v1.1.10  ok v1.2.10  ok v1.3.10  ok v1.4.10
  ok v1.5.10  ok v1.6.10  ok v1.7.10  ok v1.8.10  ok v1.9.9
```
曲线：`3/10 → 3/10 → 3/10 → 4/10 → 10/10`（前三次失败的原因依次是：删成员导致 `Cargo.lock` 失配、
漏 `crates/au4a-node/Cargo.toml`、**闸门 target 指纹假阴性**）。

## 五、已知边界（不夸大）

- 早期 tag 的 `au4a-core` **没有历史快照**（它不是任何轨道的产物），因此这些 tag 里的 core
  保持"已发布时的工作树内容"，而非该版本当时的 core。这一点是**已知且被记录的偏差**；
- 本轮重建只对 7 个 tag 的**内容**做了修正，**主分支历史未改写**（tag 指向新的修正提交，父提交保持不变）。

## 六、配套工具（`_forangent/`，不在仓库内）

| 工具 | 作用 |
|---|---|
| `gate-tag.mjs` | 本地双绿闸门（内容级比对 + 唯一 target + crate+元数据同源单元） |
| `push-tree-to-tag.mjs` | 双绿后整树固化到 tag（父提交不变、force） |
| `audit-corpus.mjs` | 已发布 tag 树 vs 本地快照的逐 crate 内容对照 |
| `diag-tag-crates.mjs` | 逐 crate 混源诊断（判定"与任何单一快照都不一致"） |
| `sync-safe.mjs` | 推送防覆盖闸门（远端有人改过的文件跳过并告警） |

## 七、教训（写给下一个维护者）

1. **"看起来对"不等于"编译得过"**：前三次修复我都是用 API 核对"树里有什么/没什么"，
   却从未把候选树真正 `cargo build` 一遍；
2. **当同一个错误在修复后"一模一样地重现"时，先怀疑工具链缓存**，而不是反复改内容；
3. **不要在 CI 上做实验**：CI 是裁判。本地闸门先双绿，再动不可逆的外部状态（force-move tag）。
